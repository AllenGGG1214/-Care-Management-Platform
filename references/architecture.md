# 养老院老人档案与独立食堂计划系统

## Architecture & Functional List

> 版本：v1.0
>
> 系统定位：独立文件型应用，不依赖 ERP、不要求对接外部采购系统。系统内部保存业务数据，并生成可发送给食堂和采购人员的独立文件。
>
> 设计状态：开发设计基线，具体技术栈、部署环境、合规要求和规模需要在技术评审时确认。

---

## 1. 业务目标与边界

### 1.1 业务目标

系统根据老人 Profile 中的健康和饮食信息，自动或半自动生成：

1. 次日早餐、午餐、晚餐食谱
2. 普通餐、低盐餐、软食等餐型的份数
3. 食堂生产计划
4. 特殊餐与分餐说明
5. 食材采购清单
6. 可打印或导出的独立文件
7. 审核、发送、修改和异常处理记录

### 1.2 系统边界

**系统内部包含：**

- 老人 Profile
- 菜谱和食材基础数据
- 饮食规则和禁忌校验
- 食谱生成
- 营养师审核
- 食堂生产计划
- 采购清单
- 文件导出
- 操作审计
- 数据备份

**明确不包含：**

- ERP 对接
- 正式采购订单自动下发
- 自动连接供应商
- 自动价格比较
- 自动付款
- 外部库存系统实时同步

后续如有需要，可以增加导入 / 导出接口，但第一版不依赖任何 ERP 或采购系统。

## 2. 推荐总体架构

### 2.1 架构风格

推荐采用**模块化单体应用 + 独立文件输出**：

- 一个后端应用承载多个业务模块
- 模块之间通过明确的服务接口协作
- 统一数据库保存业务数据
- 统一文件服务生成 Excel、PDF 或打印文件
- 不拆分为微服务，降低第一版开发和运维复杂度
- 将来规模扩大时，可独立拆出食谱、采购和通知模块

## 3. 核心业务流程

### 3.1 次日食谱与采购流程

```text
T-1 日：护理员更新老人状态
    ↓
系统读取有效老人 Profile
    ↓
系统读取菜谱、食材和饮食规则
    ↓
生成次日三餐候选食谱
    ↓
按普通餐、低盐餐、软食等餐型汇总份数
    ↓
执行过敏、禁忌、吞咽能力和状态校验
    ↓
发现冲突？ ── 是 ──> 标记异常，阻止发布，通知营养师
    │
    否
    ↓
营养师审核和调整
    ↓
冻结食谱版本
    ↓
生成食堂生产计划
    ↓
根据食谱和份数生成采购清单
    ↓
授权人员确认
    ↓
导出食谱、生产单和采购清单
    ↓
食堂与采购人员人工接收和执行
    ↓
录入实际出餐、采购和异常结果
```

### 3.2 临时变更流程

适用于新入住、请假、离院、临时禁食和饮食要求变更：

1. 授权人员修改老人状态或饮食要求。
2. 系统判断当前计划是否已发布。
3. 若未发布，直接重新计算份数和采购清单。
4. 若已发布，生成“变更版本”。
5. 重新执行过敏与禁忌校验。
6. 通知营养师和食堂主管。
7. 经确认后导出变更单。
8. 原版本保留，不允许无痕覆盖。

## 4. 后端模块详细设计

### 4.1 用户与权限模块

**职责：**

- 登录与退出
- 用户身份管理
- 角色管理
- 机构、楼栋和房间范围控制
- 页面和接口授权
- 禁止越权查看健康和饮食敏感信息

**主要接口：**

```text
POST /api/auth/login
POST /api/auth/logout
GET  /api/users/me
GET  /api/users
POST /api/users
PATCH /api/users/{userId}
GET  /api/roles
```

**关键规则：**

- 护理员只查看授权范围内老人。
- 营养师可查看与食谱相关的健康和饮食信息。
- 食堂人员只查看生产计划和特殊餐说明，不默认查看完整健康档案。
- 采购人员只查看采购清单和采购备注。
- 所有敏感信息查看行为写入审计日志。

### 4.2 老人 Profile 模块

**职责：**

- 管理老人基本档案
- 管理房间、楼栋和入住状态
- 管理饮食类型和特殊照护要求
- 管理过敏、禁忌、吞咽能力和营养要求
- 支持临时变更和生效日期

**主要接口：**

```text
GET    /api/residents
POST   /api/residents
GET    /api/residents/{residentId}
PATCH  /api/residents/{residentId}
GET    /api/residents/{residentId}/diet-profile
PUT    /api/residents/{residentId}/diet-profile
POST   /api/residents/{residentId}/status-changes
GET    /api/residents/{residentId}/history
```

**核心数据：**

```text
ResidentProfile
- resident_id
- name
- gender
- birth_date
- room_id
- building_id
- admission_status
- care_level
- effective_from
- effective_to

ResidentDietProfile
- resident_id
- meal_type
- allergies
- forbidden_ingredients
- swallowing_level
- salt_restriction
- texture_requirement
- nutrition_requirements
- food_preferences
- notes
- effective_from
- effective_to
```

### 4.3 菜谱基础数据模块

**职责：**

- 管理菜品
- 管理食材和规格
- 管理餐次
- 管理适用餐型
- 管理菜品制作说明
- 维护菜品的禁忌标签
- 维护标准食材用量

**主要接口：**

```text
GET    /api/recipes
POST   /api/recipes
GET    /api/recipes/{recipeId}
PATCH  /api/recipes/{recipeId}
GET    /api/ingredients
POST   /api/ingredients
PATCH  /api/ingredients/{ingredientId}
GET    /api/meal-types
```

**菜谱数据示例：**

```text
Recipe
- recipe_id
- dish_name
- meal_period: breakfast / lunch / dinner
- applicable_meal_types
- preparation_method
- prohibited_tags
- nutrition_tags
- active_status

RecipeIngredient
- recipe_id
- ingredient_id
- specification
- amount_per_serving
- unit
- preparation_note
```

### 4.4 规则与校验模块

**职责：**

- 校验菜品与老人 Profile 是否匹配
- 识别过敏风险
- 识别禁忌食材
- 校验餐食形态是否匹配吞咽能力
- 检查特殊餐是否有足够份数
- 检查老人状态是否有效
- 产生阻断级、警告级和提示级结果

**规则结果等级：**

| 等级 | 含义 | 处理方式 |
|---|---|---|
| 阻断 | 存在明确过敏或禁忌冲突 | 不允许发布，必须处理 |
| 警告 | 信息不完整或存在潜在风险 | 营养师确认后才能继续 |
| 提示 | 普通运营提醒 | 可继续，但需记录 |

**主要接口：**

```text
POST /api/validation/recipe-plan
GET  /api/validation/results/{planId}
POST /api/validation/results/{resultId}/resolve
GET  /api/rules
POST /api/rules
PATCH /api/rules/{ruleId}
```

### 4.5 食谱计划模块

**职责：**

- 创建计划草稿
- 选择计划日期
- 生成次日三餐
- 按餐型汇总份数
- 运行规则校验
- 提交营养师审核
- 退回、修改和重新审核
- 冻结已确认版本

**状态机：**

```text
DRAFT
  ↓
VALIDATING
  ↓
WAITING_NUTRITIONIST_REVIEW
  ↓
REWORK_REQUIRED ──> DRAFT
  ↓
APPROVED
  ↓
FROZEN
  ↓
EXPORTED / SENT
  ↓
COMPLETED
```

**主要接口：**

```text
POST /api/meal-plans
GET  /api/meal-plans?date=YYYY-MM-DD
GET  /api/meal-plans/{planId}
POST /api/meal-plans/{planId}/generate
POST /api/meal-plans/{planId}/validate
POST /api/meal-plans/{planId}/submit-review
POST /api/meal-plans/{planId}/approve
POST /api/meal-plans/{planId}/reject
POST /api/meal-plans/{planId}/freeze
POST /api/meal-plans/{planId}/regenerate
```

### 4.6 食堂生产计划模块

**职责：**

- 根据冻结食谱生成生产单
- 计算各餐次和餐型份数
- 输出特殊餐说明
- 输出备餐、分餐和出餐时间
- 支持食堂主管确认
- 记录实际出餐和替换

**主要接口：**

```text
POST /api/production-orders/from-meal-plan/{planId}
GET  /api/production-orders?date=YYYY-MM-DD
GET  /api/production-orders/{orderId}
POST /api/production-orders/{orderId}/confirm
POST /api/production-orders/{orderId}/report-exception
POST /api/production-orders/{orderId}/record-serving
```

**生产单至少包含：**

- 计划日期
- 餐次
- 菜品名称
- 总份数
- 普通餐份数
- 低盐餐份数
- 软食份数
- 特殊加工要求
- 备餐时间
- 出餐时间
- 食堂确认状态
- 异常备注

### 4.7 采购计划模块

**职责：**

- 从冻结食谱读取食材用量
- 按份数换算采购数量
- 按食材合并数量
- 应用备损比例
- 生成独立采购清单
- 允许人工调整并记录原因
- 导出采购文件

**数量换算：**

```text
采购数量
= Σ（每份标准用量 × 计划份数）
  ×（1 + 备损比例）
  - 可用库存数量
```

第一版若不维护库存，计算可以简化为：

```text
采购数量
= Σ（每份标准用量 × 计划份数）
  ×（1 + 备损比例）
```

**主要接口：**

```text
POST /api/purchase-lists/from-meal-plan/{planId}
GET  /api/purchase-lists?date=YYYY-MM-DD
GET  /api/purchase-lists/{listId}
PATCH /api/purchase-lists/{listId}/items/{itemId}
POST /api/purchase-lists/{listId}/submit
POST /api/purchase-lists/{listId}/approve
POST /api/purchase-lists/{listId}/export
```

**采购清单字段：**

- 采购日期
- 使用日期
- 食材名称
- 规格
- 数量
- 单位
- 使用餐次
- 关联菜品
- 采购备注
- 状态
- 调整原因

### 4.8 文件导出模块

**职责：**

- 生成食谱文件
- 生成食堂生产单
- 生成采购清单
- 生成打印友好版本
- 保存文件版本
- 提供下载和重新导出

**输出文件：**

```text
YYYY-MM-DD_次日食谱.xlsx
YYYY-MM-DD_食堂生产单.xlsx
YYYY-MM-DD_采购清单.xlsx
YYYY-MM-DD_特殊餐说明.pdf
```

**导出控制：**

- 文件必须包含计划日期和版本号。
- 已冻结版本不可静默覆盖。
- 重新导出必须保留导出记录。
- 文件内容只包含接收角色所需的最小信息。

### 4.9 通知与异常模块

**职责：**

- 待审核提醒
- 过敏冲突提醒
- 特殊餐不足提醒
- 食堂无法执行提醒
- 采购清单未确认提醒
- 临时变更提醒

第一版可以使用站内通知和页面提醒；短信、企业微信或邮件属于后续扩展。

### 4.10 审计与备份模块

**职责：**

- 生成数据库备份

- 支持恢复演练

## 6. API 设计原则

### 6.1 通用原则

- 使用 HTTPS。
- 使用 JSON 请求和响应。
- 所有业务对象使用唯一 ID。
- 所有写操作返回版本号和更新时间。
- 所有列表接口支持分页、筛选和排序。
- 所有重要操作必须写审计日志。
- 不使用物理删除覆盖历史业务记录；采用状态或归档。

### 6.2 统一响应格式

```json
{
  "success": true,
  "data": {},
  "error": null,
  "requestId": "request-id"
}
```

错误示例：

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "ALLERGY_CONFLICT",
    "message": "食谱包含老人禁忌食材，计划不能发布"
  },
  "requestId": "request-id"
}
```

## 13. 架构决策记录

### ADR-001：采用模块化单体而非微服务

**状态：** Proposed

**背景：**

第一版需要快速验证老人 Profile、食谱、食堂生产和采购文件流程。当前没有 ERP 集成要求，也没有明确的大规模并发需求。

**决策：**

采用模块化单体后端。业务模块在代码和数据库层面保持边界，但第一版统一部署。

**优点：**

- 开发和部署简单
- 适合小团队
- 数据一致性更容易控制
- 食谱、生产单和采购清单可以在一个事务边界内生成
- 后续仍可拆分服务

**代价：**

- 模块之间需要严格控制依赖
- 单体部署故障可能影响多个功能
- 后续拆分需要补充服务通信和数据边界

### ADR-002：采用独立文件交付而非 ERP 集成

**状态：** Proposed

**背景：**

用户明确要求系统与 ERP 无关，食堂和采购人员通过独立文件接收计划。

**决策：**

第一版生成 Excel、PDF 或打印友好的独立文件，由授权人员下载、打印或通过内部渠道发送。

**代价：**

- 采购状态不会自动回写系统
- 文件发送依赖人工流程
- 需要严格管理文件日期和版本

### ADR-003：自动生成建议，人工审核发布

**状态：** Proposed

**背景：**

老人健康、过敏和饮食要求属于高风险业务信息，不能仅依赖自动规则发布。

**决策：**

系统自动生成食谱和采购建议，但必须经过营养师审核，随后由授权人员发布或导出。

**代价：**

- 流程增加审核步骤
- 未审核计划不能进入最终生产流程
- 需要异常提醒和待办管理

## 15. 结论

该系统应先建设为一个独立、可审计、以文件交付为核心的养老院膳食运营平台：

```text
老人 Profile
    → 食谱生成
    → 规则校验
    → 营养师审核
    → 食堂生产单
    → 采购清单
    → 独立文件交付
```

第一版不依赖 ERP，优先保证三件事：

1. 老人的饮食要求不会被遗漏。
2. 食堂拿到清晰、可执行的生产信息。
3. 采购人员拿到可核对、可导出的食材清单。
